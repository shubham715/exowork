# WhatsApp management

The admin sidebar contains **WhatsApp Management → API settings, Templates, Logs**.

API settings reuse the encrypted communication settings already available under Masters & settings. Templates contains 13 proposal-based messages, including the Hindi interview reminder and day 7/15/30 retention checks. Each entry documents the exact Meta body, language, category, sample variables, recipient and trigger.

## Enable live messaging

1. Set `APP_URL` to the public HTTPS application URL. This is the base for authenticated candidate and center links generated by the scheduler. Restart workers after changing environment settings.
2. Configure WhatsApp credentials under API settings; configure and verify the signed webhook using its displayed callback URL.
3. Add client-approved career and interview preparation video URLs using **Templates → Video links**. Messages that need a video wait until the relevant link is configured.
4. Submit the displayed text templates to Meta, either from the library or in WhatsApp Manager. Use the exact body, positional variables and displayed language. These templates use authenticated portal choices rather than interactive message buttons.
5. Sync Meta status, then Approve each template for EXOWORK use. Admin rejection disables app use; it does not change Meta's approval. Modified content, additional components and an account switch require a fresh sync/review. Test previews are available before approval; sending requires both approvals.
6. Run a Laravel database queue worker continuously and Laravel's scheduler every minute. Manage them with the hosting platform's process supervisor / scheduled task system:

```sh
php artisan migrate --force
php artisan queue:work database --sleep=3 --timeout=60 --tries=1
php artisan schedule:run
```

`schedule:run` must run once per minute. `php artisan schedule:work` is an alternative for local development. `php artisan whatsapp:process` performs one workflow/outbox scan. The database queue's `retry_after` must exceed the worker timeout (the default 90 seconds does). Do not run multiple scheduler processes without a shared locking cache.

## Workflow behavior

- Welcome messages apply to candidate registrations after the management migration. Existing candidates are not automatically welcomed again.
- Interested candidates in ongoing training are deferred when their batch ends more than 15 calendar days away. The 15-day boundary is inclusive and uses India dates. Ready, available candidates receive the video and eligible job recommendations; employer identity and description are omitted from recommendation messages. Up to three new eligible recommendations are queued per candidate per scan.
- New applications receive interview availability prompts. Scheduling and rescheduling send confirmed details; Hindi reminders run one calendar day before the interview. Staff record selection and joining through the saved admin operations forms. Center notifications require the center SPOC's explicit WhatsApp consent, available on the center profile.
- Actual joined placements receive checks on days 7, 15 and 30. Candidate portal responses also support day 3 and 90 views. Reported employment concerns create call tasks; subsequent checks stop after a reported departure.
- Authenticated portal responses store interest, availability, attendance and retention outcomes. Availability creates a call task. Doubt / inability to attend and employment concerns create follow-ups. Delivered welcome messages without a response after 24 hours and delivered interview reminders without a response after 6 hours also create de-duplicated call tasks. Assigned agents are preferred; otherwise an active agent/admin owns the task.
- Scheduled scans de-duplicate notifications with unique event keys. Recipient messages are spaced by at least six seconds in the outbox. The scheduler recovers queued rows if dispatch was interrupted.

## Delivery and resend controls

All outbound sends, including candidate messaging, test sends and resends, go through `SendWhatsAppMessage`. Variables are encrypted at rest because the worker and retries need them. The log API never exposes the stored payload. Workers reload saved credentials and recheck active profiles, consent, phone changes, opt-outs and current Meta approval/content before posting.

The statuses are queued, submitting, accepted, sent, delivered, read, failed, skipped and unknown. Accepted means Meta returned a message ID; signed webhooks confirm later delivery states. A timeout, server error or interrupted submission may already have sent a message, so unknown records cannot be resent from Logs. Review them in WhatsApp Manager first.

Single and bulk resend create a new record linked to the failed attempt, preserve its original status, and prevent duplicate retry requests. Only failed messages with saved variables and no existing retry are eligible. Legacy messages without an encrypted payload cannot be resent. Opted-out or changed candidates are suppressed. A failure of the retry can be retried from that new record.

Meta error details are mapped to actionable descriptions without disclosing credentials or raw provider responses. The exact error code and provider message ID remain visible to authorised administrators. STOP and equivalent opt-out replies suppress future candidate and center sends.

## Verification

```sh
php artisan test
npm run build
```

The tests fake Meta and use isolated test databases. They do not send real WhatsApp messages. Live approval, delivery and read-receipt verification require a configured Meta account, approved templates, a consenting test recipient, a running worker and a public HTTPS webhook.
